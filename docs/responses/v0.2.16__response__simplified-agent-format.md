## 1. Implementation Plan for Phase 1 (The `.issues` Parser)

### Summary

Phase 1 delivers the `.issues` flat file parser and its integration into the existing `Graph__Repository` loading pipeline. The parser reads `.issues` files from storage, parses each line into the existing `Schema__Node` data model, infers hierarchy from indentation, infers issue types from `[type]` prefixes, resolves `->` cross-references, and produces the same in-memory graph that the current JSON-per-issue structure produces.

### Step-by-Step Plan

**Step 1: Define parser schemas (pure data, no logic)**

Create Type_Safe schema classes for the intermediate parse results:
- `Schema__Issues_File__Line` -- one parsed line (label, status, description, indent level, explicit type, cross-ref targets)
- `Schema__Issues_File__Parse_Result` -- all parsed lines from one file, plus the source file path
- `Schema__Issues_File__Parse_Error` -- a single parse error (line number, raw line, error message)
- `Schema__Issues_File__Validation_Result` -- aggregate result with errors, warnings, and parsed data

**Step 2: Build the line parser**

Create `Parser__Issues_File__Line` -- a stateless service that takes a raw string line and returns a `Schema__Issues_File__Line`. This class handles:
- Pipe-delimited splitting (`label | status | description`)
- Tab-indentation counting (depth level)
- `[type]` prefix extraction from the label field
- `-> target-label` extraction from the description field
- Whitespace trimming on each field

**Step 3: Build the file parser**

Create `Parser__Issues_File` -- a service that takes file content (full string) and returns a `Schema__Issues_File__Parse_Result`. This class handles:
- Line-by-line parsing via `Parser__Issues_File__Line`
- Blank line / comment line skipping (lines starting with `#`)
- Accumulating `Schema__Issues_File__Parse_Error` entries for unparseable lines
- Building the ordered list of parsed lines with their indent depths

**Step 4: Build the hierarchy resolver**

Create `Resolver__Issues_File__Hierarchy` -- a service that takes a `Schema__Issues_File__Parse_Result` and resolves parent-child relationships based on indentation. This class handles:
- Maintaining an indent-depth stack to track the current parent at each level
- For each line, determining its parent by comparing indent depth to the stack
- Assigning the default link type (`has-task`) for parent-child relationships
- Producing a list of parent-child pairs (parent_label, child_label, link_verb)

**Step 5: Build the cross-reference resolver**

Create `Resolver__Issues_File__Cross_Refs` -- a service that takes parsed lines and resolves `->` cross-references. This class handles:
- Extracting target labels from `-> label` syntax in description fields
- Assigning default link type (`relates-to` or `depends-on`)
- Validating that target labels exist in the parsed data (or flagging as warnings for cross-file resolution)

**Step 6: Build the issue type inferrer**

Create `Inferrer__Issues_File__Type` -- a service that infers issue types when not explicitly provided via `[type]` prefix. Rules:
- If `[type]` prefix is present, use it directly
- If the label matches a known pattern (e.g., ends with `?`), infer `question`
- Top-level items default to `task`
- Indented items default to `sub-task` (or `task` if no `sub-task` type is registered)
- The inferrer consults the existing node types configuration (`config/node-types.json`) when available

**Step 7: Build the node factory**

Create `Factory__Issues_File__Nodes` -- a service that converts parsed, resolved data into `Schema__Node` instances. This class handles:
- Generating `Node_Id` for each issue
- Computing sequential `node_index` per type
- Building `Safe_Str__Node_Label` from the parsed label (validating against `Safe_Str__Node_Label` regex -- this is a critical design point, see Section 6)
- Setting `created_at` / `updated_at` timestamps
- Creating `Schema__Node__Link` entries for hierarchy and cross-references

**Step 8: Integrate into Graph__Repository loading pipeline**

Modify `Graph__Repository` to:
- Add a method `issues_files_load()` that scans storage for `*.issues` files
- Call the parser pipeline (Steps 2-7) for each file found
- Merge the resulting `Schema__Node` instances with any existing JSON-based nodes
- Handle label collisions (report as errors, do not overwrite)

**Step 9: Create the integration service**

Create `Issues_File__Loader__Service` -- the top-level orchestrator that:
- Coordinates scanning, parsing, resolving, and loading
- Returns a comprehensive result with all issues loaded and all errors/warnings
- Is the single entry point that `Graph__Repository` calls

### Execution Order

Steps 1-6 can be developed and tested independently (they have no dependencies on each other beyond the schemas from Step 1). Step 7 depends on Steps 2-6. Step 8 depends on Step 7. Step 9 ties everything together.

Recommended implementation order for minimum viable parser:
1. Step 1 (schemas) + Step 2 (line parser) + tests
2. Step 3 (file parser) + tests
3. Step 4 (hierarchy) + Step 5 (cross-refs) + tests
4. Step 6 (type inference) + tests
5. Step 7 (node factory) + tests
6. Steps 8-9 (integration) + integration tests

## 3. Where the Parser Plugs Into the Existing Codebase

### Integration Point: `Graph__Repository`

The primary integration point is `Graph__Repository`, which is the storage-agnostic data access layer. Currently it loads nodes by scanning for `issue.json` files in the `data/{node_type}/{label}/` folder structure. The parser plugs in by adding a new loading path:

```
Graph__Repository
  |
  |-- node_load()              (existing: loads from data/{type}/{label}/issue.json)
  |-- nodes_list_all()         (existing: scans for all issue.json files recursively)
  |
  |-- issues_files_load()      (NEW: scans for *.issues files, parses, returns Schema__Node list)
  |-- issues_files_scan()      (NEW: finds all *.issues file paths in storage)
```

The `issues_files_load()` method:
1. Calls `issues_files_scan()` to find all `.issues` files in the storage
2. For each file, reads content via `storage_fs.file__str()`
3. Passes content to `Issues_File__Loader__Service` which runs the full pipeline
4. Returns the list of `Schema__Node` instances and a list of errors

### Integration Point: `Node__Service`

`Node__Service.list_nodes()` currently calls `self.repository.nodes_list_all()` which only finds `issue.json` files. After integration, it also calls `self.repository.issues_files_load()` and merges results. Alternatively, `nodes_list_all()` itself can be extended to include issues from `.issues` files -- this is an architectural decision about whether `.issues` nodes are "first class" in the storage layer or a separate overlay.

**My recommendation:** Keep it in `Graph__Repository` as a separate method initially. The `Issues_File__Loader__Service` produces `Schema__Node` instances that are identical to JSON-loaded ones, so higher layers (Node__Service, Link__Service) do not need to change. The merging happens at the repository level.

### Storage Layer

The parser reads `.issues` files through the same `Storage_FS` abstraction that everything else uses. This means it works with Memory-FS (for tests), local disk, S3, SQLite, and ZIP backends without any backend-specific code.

### File Discovery

`.issues` files can live:
- At the storage root (e.g., `workstream-observability.issues`)
- In subdirectories (e.g., `workstreams/observability.issues`)

The scanner should look for any file matching `*.issues` or `*.issuesfs` anywhere in the storage tree.

### Potential Blocker: Label Format Mismatch

**This is the most critical design question for the Architect.**

The brief proposes labels like `enable-cloudfront-logs` (lowercase, hyphenated, descriptive). The existing `Safe_Str__Node_Label` regex enforces `^[A-Z][a-zA-Z]*(-[A-Z][a-zA-Z]*)*-\d{1,5}$` -- meaning labels must be `Word-Number` format (e.g., `Task-15`, `Bug-27`, `Git-Repo-1`).

The `.issues` file labels fundamentally conflict with this regex. Options:

1. **Create a new `Safe_Str__Issues_File__Label` type** with a permissive regex (e.g., `^[a-z][a-z0-9-]+$`) and use it only in the parser. The node factory then generates a conforming `Safe_Str__Node_Label` (e.g., `Task-1`) and stores the original `.issues` label as the `title` or a property.

2. **Relax `Safe_Str__Node_Label` regex** to accept both formats. This changes a fundamental type contract and affects all existing code.

3. **Use the `.issues` label as the title** and auto-generate conforming labels during parsing (e.g., `enable-cloudfront-logs` becomes `Task-1` with title "Enable CloudFront access logs with IP masking").

4. **Create a second label field** -- a "slug" or "alias" that holds the `.issues` label for cross-referencing, while the canonical `label` field holds the `Word-N` format.

**My recommendation as Dev:** Option 1 or Option 3. The parser should use `Safe_Str__Issues_File__Label` internally and produce valid `Safe_Str__Node_Label` values for the output `Schema__Node`. The mapping strategy (how `.issues` labels become `Schema__Node` labels) is an Architect decision. I can implement any of these, but I need a decision before the node factory (Step 7) can be finalized.

**Action:** I will raise this as a Blocker to the Conductor for routing to the Architect.

### Potential Blocker: Default Link Type Configuration

The brief says parent-child indentation implies `has-task` links. Currently, `has-task` must exist in `config/link-types.json` with valid source/target type constraints. The parser needs to either:
- Require that `has-task` is pre-configured (and fail with a clear error if not)
- Auto-register default link types during parsing

**My recommendation:** Require pre-configuration for Phase 1. Auto-registration is Phase 3 (schema management) territory.

### Potential Blocker: Node Index Generation

The existing system tracks per-type sequential indexes via `Schema__Type__Index` stored in `data/{type}/_index.json`. The parser creates many nodes at once. It needs to either:
- Load existing type indexes, increment for each new node, and save back
- Or defer index management to the merge step

**My recommendation:** The node factory loads existing type indexes from the repository, increments as it creates nodes, and saves the updated indexes. This is the same logic that `Node__Service.create_node()` already does -- I will extract the shared logic into a helper.

```
        |
        +---> Resolver__Issues_File__Cross_Refs  -- "-> label" -> link pairs
        |
        +---> Inferrer__Issues_File__Type        -- [type] prefix / context -> node type
        |
        v
  Factory__Issues_File__Nodes     -- combine all resolved data
        |
        v
  List[Schema__Node]              -- same type as JSON-loaded nodes
        |
        v
  Graph__Repository               -- merge into existing graph
```

## 8. Open Questions for Architect

1. **Label format:** How should `.issues` file labels (lowercase-hyphenated like `enable-cloudfront-logs`) map to `Safe_Str__Node_Label` values (which enforce `Word-N` format like `Task-1`)? See Section 6 for options.

2. **Write-back:** Should the parser support writing modified `Schema__Node` data back to `.issues` format? The brief mentions `.issues` files as an "input format" but the normalisation command (Phase 4) writes JSON. Is `.issues` -> `.issues` round-tripping in scope?

3. **File extension:** The brief mentions both `.issues` and `.issuesfs`. Should we support both? My recommendation: support both, with `.issues` as primary.

4. **Comment syntax:** The brief does not mention comments in `.issues` files. I propose supporting `#` as a line comment prefix. Is this acceptable?

5. **Status vocabulary:** The brief uses `todo`, `in-progress`, `done`, `blocked`. The existing `Enum__Issue__Status` uses `backlog`, `todo`, `in-progress`, `review`, `done`. Should the parser accept any status string (matching `Safe_Str__Status` regex `^[a-z][a-z0-9-]*$`) or only the predefined enum values?

## 9. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Label format mismatch blocks node factory | High | Raise Blocker immediately; implement parser layers 1-6 without depending on label decision |
| Tab vs spaces in indentation | Medium | Standardize on tabs only (as the brief specifies); reject spaces-as-indentation with clear error |
| Large `.issues` files (1000+ lines) | Low | Parser is line-by-line, memory overhead is proportional to line count; no concerns |
| Cross-file reference resolution order | Medium | Two-pass approach: first pass parses all files, second pass resolves cross-refs against the full label set |
| Merge conflicts between `.issues` and JSON nodes | Medium | Label uniqueness check across both sources; fail with clear error on collision |
